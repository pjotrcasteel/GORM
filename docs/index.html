Why a graph ORM?

Relationships are data, not an afterthought.

Traditional persistence code often treats relationships as joins hidden behind repositories. GORM promotes nodes, edges and graph traversal to first-class concepts while keeping the API strongly typed.

01

Persist the topology

Map nodes and edges explicitly. Track connects and disconnects alongside ordinary entity changes.

02

Query the relationship

Use outgoing, incoming and chained traversals rather than rebuilding graph intent from ad-hoc joins.

03

Keep tests fast

Use the same graph model with in-memory execution for unit tests and Reqnroll scenarios without a SQL dependency.

04

Inspect graph evolution

Capture node and edge history, query a point in time, and reason about how connected state changed.

OUTGOING TRAVERSAL

Follow dependencies from the API.

Outgoing and chained traversal make relationship intent part of the query instead of hiding it in join plumbing.

var dependencies = await context.Set<ServiceNode>()
    .Where(x => x.Name == "api")
    .Outgoing<DependsOnEdge, ServiceNode>()
    .ToListAsync();
The core API shape

Nodes and edges stay ordinary CLR types.

public sealed class PersonNode : Node
{
    public string Name { get; set; } = string.Empty;
    public List<ProjectNode> Projects { get; set; } = [];
}

public sealed class WorksOnEdge : Edge
{
    public bool IsPrimary { get; set; }
}
var projects = await context.Set<PersonNode>()
    .Where(x => x.Id == personId)
    .Outgoing<WorksOnEdge, ProjectNode>()
    .ToListAsync();

var person = await context.Set<PersonNode>()
    .Include(x => x.Projects)
    .SingleAsync();

Beyond core persistence

The graph becomes a runtime model you can inspect.

The current implementation already extends beyond CRUD. The public surface keeps those capabilities subordinate to the core ORM instead of presenting five unrelated products.

CORE

Graph ORM

Typed model configuration, node/edge sets, traversal, includes, change tracking and graph mutations.

TIME

Temporal graph

History capture plus AsOf, Current and range queries for point-in-time graph inspection.

ANALYSIS

Graph intelligence

Centrality, routing, components, communities, impact and versioned projections over ordinary GORM entities.

SIMULATION

Digital twin

Isolated graph scenarios for drift, outage rehearsal and reproducible risk analysis without implicit persistence.

GROUNDING

Explainable GraphRAG

Path-aware evidence and graph-scoped citations with security boundaries kept explicit.

QUERY

Helix

Query analysis, generated SQL inspection, safe rewrites and strict policy for graph-query execution.

WRITE PLAN

ChangeSet compiler

Preview graph writes as an ordered plan, preserve rollback semantics and explain concurrency conflicts.

Boundary

GORM owns graph persistence mechanics—not your domain policy.

Analysis, previews and simulations remain read-only until the application explicitly chooses a mutation or save operation. In-memory execution exists for deterministic tests, not as a claim that SQL Server behavior is irrelevant.
