GORM DOCUMENTATION

Graph persistence that feels like .NET.

GORM is a strongly typed graph ORM for SQL Server Graph. It keeps nodes and edges explicit, lets queries express relationship intent directly and gives the same model a fast in-memory execution path for tests.

GET STARTED

Build your first graph

Start with two node types and one relationship. GORM keeps the model ordinary: your domain entities remain CLR types while the persistence layer understands which types are nodes and which are edges.

1

Define nodes

A node is an entity that participates in graph relationships.

public sealed class PersonNode : Node
{
    public string Name { get; set; } = string.Empty;
}

public sealed class ProjectNode : Node
{
    public string Name { get; set; } = string.Empty;
}
2

Define an edge

An edge can carry data of its own.

public sealed class WorksOnEdge : Edge
{
    public bool IsPrimary { get; set; }
}
3

Traverse the relationship

Relationship direction becomes part of the query instead of being reconstructed from manual joins.

var projects = await context.Set<PersonNode>()
    .Where(x => x.Id == personId)
    .Outgoing<WorksOnEdge, ProjectNode>()
    .ToListAsync();

YOUR FIRST MODEL

Keep domain types normal

Node and edge classes stay focused on domain data. Public scalar properties are conventionally mapped; navigation properties represent relationships instead of ordinary scalar columns.

NODE
public sealed class ServiceNode : Node
{
    public string Name { get; set; } = "";
    public ServiceState State { get; set; }
}
EDGE
public sealed class DependsOnEdge : Edge
{
    public string Kind { get; set; } = "runtime";
}
CORE CONCEPTS

Nodes and edges are first-class persistence concepts

Traditional ORMs usually make relationships feel secondary to tables. GORM treats the relationship itself as data: it has a type, direction, identity and optionally its own properties.

NODE

Things

People, services, projects, devices or any other domain entity that participates in the graph.

EDGE

Connections

Works on, depends on, owns, routes to or any other typed relationship between nodes.

TRAVERSAL

Intent

Queries can ask for connected nodes directly rather than hiding the graph path behind join mechanics.

IDENTITY & MAPPING

Identity follows a simple default

Id is the default key for nodes and edges. Public scalar properties are conventionally mapped while relationship navigation stays graph-aware.

RELATIONSHIPS

Direction is explicit

Outgoing and incoming traversal let query code say which way it moves through the graph. Connect and disconnect operations are tracked alongside ordinary entity changes.

CHANGE TRACKING

Track topology changes with entity changes

Graph mutations are part of the same persistence model. A save can reason about node changes, edge changes, connections and disconnections as explicit work.

QUERYING

Start with familiar LINQ

Node-root queries remain LINQ-shaped. Filters, projections, paging and aggregates stay familiar, then graph-specific operators add relationship intent where required.

var active = await context.Set<ServiceNode>()
    .Where(x => x.State == ServiceState.Active)
    .OrderBy(x => x.Name)
    .Take(25)
    .ToListAsync();
TRAVERSAL

Query the relationship directly

Traversal is where GORM differs most visibly from a conventional ORM. The graph path becomes part of the query shape.

OUTGOING
context.Set<ServiceNode>()
    .Where(x => x.Id == serviceId)
    .Outgoing<DependsOnEdge, ServiceNode>()
INCOMING
context.Set<ServiceNode>()
    .Where(x => x.Id == serviceId)
    .Incoming<DependsOnEdge, ServiceNode>()
RELATED DATA

Use Include when the object graph matters

Traversal is ideal when the path is the question. Include and ThenInclude are useful when you want the connected object graph materialized for application code.

var person = await context.Set<PersonNode>()
    .Include(x => x.Projects)
    .SingleAsync(x => x.Id == personId);
GENERATED SQL

Make translation inspectable

A graph ORM should not make its SQL mysterious. The documentation playground makes the LINQ-to-SQL shape visible, and Helix is intended to expose query analysis and SQL inspection as a first-class capability.

TEMPORAL GRAPH

Ask what the graph looked like before

GORM can capture node and edge history so a point-in-time query reconstructs connected state, not only scalar row snapshots.

var snapshot = await context.Set<ServiceNode>()
    .AsOf(incidentStartedAt)
    .ToListAsync();
TESTING

Use the same model in memory

In-memory execution keeps unit and BDD tests fast and deterministic. It does not pretend provider behavior is irrelevant; SQL Server integration tests still validate provider-specific behavior.

GRAPH INTELLIGENCE

Analyze ordinary GORM entities

Centrality, routing, components, communities, impact analysis and versioned projections operate over the same graph model instead of forcing a second representation.

CHANGESET COMPILER

Preview graph writes as a plan

The ChangeSet compiler is intended to make graph mutations inspectable before application, preserve rollback semantics and explain concurrency conflicts rather than hiding them.

API SHAPE

Core operations at a glance

Set<TNode>()Start a typed node-root query.
Outgoing<TEdge,TTarget>()Traverse an outgoing typed edge.
Incoming<TEdge,TSource>()Traverse an incoming typed edge.
Include(...)Load relationship navigation.
AsOf(...)Query graph state at a point in time.
Current()Restrict a temporal graph query to current state.
PROVIDERS

Production and test execution have different jobs

SQL Server Graph is the production persistence target. The in-memory provider exists for deterministic test execution, not as a claim of provider equivalence.

DESIGN BOUNDARY

GORM owns persistence mechanics, not your business policy

Mapping, translation, change tracking, graph history and graph persistence are framework concerns. Whether a change should happen remains an application decision.

REPOSITORY STATUS

The public surface comes before source migration

The repository intentionally establishes naming, documentation and product boundaries before the existing implementation source is migrated and packaged. This documentation should therefore distinguish documented API direction from a published binary contract.
